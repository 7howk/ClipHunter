# ClipHunter Frontend — регламент агента клиентской разработки

Этот файл — инструкция для AI-агента (Claude Code, Codex, Cursor и др.), который
разрабатывает клиентскую часть ClipHunter. Он дополняет корневой `AGENTS.md`
и не противоречит ему. Если правило здесь и в корне расходятся, действует
более строгое.

Агент работает в каталоге `frontend/` и отвечает за всё, что видит и делает
пользователь в браузере: страницы, компоненты, состояние, работу с API,
доступность, адаптивность, визуальный стиль и тесты клиента.

---

## 1. Продукт и задача клиента

**ClipHunter** ищет интересные моменты в длинных записях стримов и игровых
сессий: пользователь загружает видео, backend расшифровывает речь (Whisper),
оценивает фрагменты (LLM), а клиент показывает найденные моменты с
таймкодами и позволяет нарезать выбранные в клипы для Shorts, TikTok и т. п.

Клиент решает три задачи:

1. **Лендинг (`/`)** объясняет, что делает продукт, и ведёт к загрузке.
2. **Загрузка (`/upload`)** принимает файл, проверяет его до отправки и
   запускает обработку.
3. **Проект (`/projects/:projectId`)** показывает прогресс, найденные моменты,
   плеер с таймлайном, выбор и нарезку клипов.

Главный продуктовый принцип, который клиент обязан соблюдать: **не выдумывать
хайлайты**. Пустой результат показывается честно, имитация данных всегда
явно помечена.

## 2. Зона ответственности

| Можно                                                           | Нельзя без явной просьбы владельца                   |
| --------------------------------------------------------------- | ---------------------------------------------------- |
| Всё внутри `frontend/`                                          | Код в `backend/` и `infra/`                          |
| Сервис `web` в `infra/docker-compose.yml` и job `frontend` в CI | Схемы БД, миграции, контракт API на стороне backend  |
| Предлагать изменения контракта API в PR-описании                | Менять контракт молча, «подгоняя» backend под клиент |

Если клиенту нужно то, чего нет в API, агент **не обходит backend**, а:
добавляет имитацию по контракту (см. раздел 6) и пишет в отчёте, какой
endpoint нужен.

## 3. Стек

| Задача            | Технология                                                 | Почему                                    |
| ----------------- | ---------------------------------------------------------- | ----------------------------------------- |
| UI                | React 19 + TypeScript (strict, `noUncheckedIndexedAccess`) | типобезопасность до индексов массивов     |
| Сборка            | Vite                                                       | быстрый dev-сервер, прокси `/api`         |
| Состояние сервера | RTK Query                                                  | кеш, теги инвалидации, polling из коробки |
| Состояние клиента | Redux Toolkit (`createSlice` + `selectors`)                | предсказуемо, тестируется без UI          |
| Маршрутизация     | React Router (data router, `lazy`)                         | лендинг не тянет код рабочих страниц      |
| Стили             | CSS Modules + токены `src/app/styles/tokens.css`           | изоляция без runtime-CSS-in-JS            |
| Иконки            | `lucide-react`                                             | один набор, одна толщина линии            |
| Графика маскота   | WebGL-шейдер без библиотек                                 | см. раздел 8                              |
| Качество          | ESLint, Prettier, Steiger (FSD), Vitest + Testing Library  | всё запускается одной командой            |

Новую зависимость добавляют, только если без неё задачу нельзя решить
разумным объёмом кода. В отчёте объясняют, зачем она нужна.

## 4. Архитектура: Feature-Sliced Design

```text
src/
├── app/        инициализация: store (model/), роутер, layout, глобальные стили, токены
├── pages/      страницы; блоки, нужные только одной странице, живут в её ui/
├── widgets/    крупные блоки, общие для нескольких страниц (шапка, футер)
├── features/   действия пользователя: upload-video, select-highlights, generate-clips
├── entities/   доменные сущности API: project, highlight, clip, system
└── shared/     api (baseApi, контракты, имитация), config, lib, ui-kit
```

### Правила импортов

- Слой импортирует **только нижележащие**: `app → pages → widgets → features → entities → shared`.
- Слайсы одного слоя друг друга не импортируют.
- В чужой слайс заходят только через его `index.ts` (публичный API).
  Внутри слайса — относительные импорты.
- `app` не импортирует никто. Тесты тоже: им нужен локальный store (раздел 9).

Это проверяют два инструмента, и оба должны быть зелёными:
ESLint (`no-restricted-imports`) и Steiger (`npm run lint:fsd`).

### Куда положить новый код

| Что это                                                           | Куда                                 |
| ----------------------------------------------------------------- | ------------------------------------ |
| Endpoint API, тип ответа сущности, её UI-карточка                 | `entities/<сущность>/{api,model,ui}` |
| Действие пользователя с состоянием (выбрать, загрузить, нарезать) | `features/<действие>/{model,ui,lib}` |
| Блок страницы, используемый на одной странице                     | `pages/<страница>/ui/`               |
| Тот же блок понадобился второй странице                           | перенести в `widgets/<блок>/`        |
| Чистая функция без React и домена (форматирование, WebGL)         | `shared/lib/`                        |
| Базовый UI-компонент без доменной логики                          | `shared/ui/<компонент>/`             |
| DTO и формат ошибок API                                           | `shared/api/contracts.ts`            |

Сегменты называются по назначению (`api`, `model`, `ui`, `lib`, `config`),
а не по типу (`components`, `hooks`, `store`).

## 5. Состояние

- **Данные с сервера — только RTK Query.** Сущность регистрирует endpoints
  через `baseApi.injectEndpoints`. Ответы API не копируются в слайсы.
- **Теги кеша:** `Project`, `Highlight`, `Clip`. Мутация инвалидирует то, что
  меняет; списки используют тег `{ type, id: 'LIST' }`.
- **Polling** включается только пока данные реально меняются (статус
  `processing`, клип не готов). Чтобы выключить опрос без эффекта, состояние
  читают из кеша до подписки (`endpoint.useQueryState`), как в `ProjectPage`.
- **Клиентское состояние** (выбор моментов, blob-URL превью, запрошенные
  клипы) — слайсы рядом с владельцем. Селекторы описаны в `selectors`
  слайса и принимают `<Slice>RootState`, поэтому нижние слои ничего не знают
  о корневом store.
- В store хранится только сериализуемое: строки, числа, массивы id.

## 6. Интеграция с backend

### Режимы API (`VITE_API_MODE`)

| Режим                   | Что происходит                                                    | Когда использовать                |
| ----------------------- | ----------------------------------------------------------------- | --------------------------------- |
| `hybrid` (по умолчанию) | Реализованное backend идёт в настоящий API, остальное имитируется | обычная разработка и демонстрация |
| `real`                  | только настоящий API                                              | проверка готового backend         |
| `mock`                  | весь API в браузере, backend не нужен                             | показ без Docker, тесты           |

Маршрутизацию делает `shared/api/hybridBaseQuery.ts`. Список имитируемых
маршрутов — функция `isSimulatedPipelineRoute` в `shared/api/mock/mockBaseQuery.ts`.

### Что сейчас реализует backend

`GET /health`, `POST /projects`, `GET /projects`, `GET /projects/{id}`,
`GET /projects/{id}/status`, `POST /projects/{id}/upload`.

Загрузка — **поток в теле запроса, не multipart**: имя файла в query
`filename`, `Content-Type` соответствует расширению (`getVideoContentType`).
Лимиты: 500 МБ и 30 минут, валидируются и на клиенте, и на сервере.

Имитируются: `POST /projects/{id}/process`, `GET /projects/{id}/highlights`,
`/highlights/*`, `/clips/*`.

### Рецепт: backend реализовал новый этап

1. Сверить схемы в `backend/src/cliphunter/application/dto.py` и
   `presentation/http/*.py` с `shared/api/contracts.ts`, обновить типы.
2. Убрать маршрут из `isSimulatedPipelineRoute`.
3. Обновить имитацию, чтобы режим `mock` по-прежнему повторял контракт.
4. Поправить тесты `hybridBaseQuery.test.ts` и `mockBaseQuery.test.ts`.
5. Проверить сценарий в браузере против настоящего backend (раздел 10).
6. Обновить таблицу в `frontend/README.md` и текст `DemoApiNotice`.

### Ошибки

Backend отвечает в едином формате `{ "error": { "code", "message" } }`.
Сообщение для пользователя получают через `getErrorMessage` из `shared/api`.
Текст ошибки говорит, **что случилось и что делать**, без извинений.

## 7. Дизайн-система

Стиль задан референсом «пиксельный hero со сканлайнами»: монохромная
«бумага» монитора, пиксельные заголовки, моноширинный текст, один акцент.

- **Цвета и отступы** — только из `tokens.css`. Сетка 4 px. Новые «сырые»
  hex-значения в компонентах запрещены.
- **Шрифты:** Press Start 2P — только крупные заголовки (`PixelHeading`),
  IBM Plex Mono — весь остальной текст. Начертания 400 и 500.
- **Акцент один:** `--rec` (красная лампочка записи). Им отмечают активный
  момент, playhead и ошибки. Больше нигде.
- **Фирменная деталь:** уголки рамки захвата (`CaptureFrame`) — только у
  активного момента.
- **Не использовать:** градиентный текст, цветные свечения, эмодзи вместо
  иконок, надписи КАПСОМ с разрядкой над заголовками, `transition: all`,
  бесконечные анимации у неживых элементов.
- **Motion:** анимируются только `transform`, `opacity`, цвет. Одна кривая
  `--ease`. `prefers-reduced-motion` уважается всегда.
- **Тексты** на русском, по-человечески: кнопка называет действие
  («Найти лучшие моменты», а не «Отправить»), без восклицательных знаков и
  точек в коротких подписях.

## 8. Маскот Бобби

`shared/ui/mascot`: сцена рисуется на 2D-canvas (`bobbyScene.ts`), WebGL-шейдер
(`shared/lib/scanline`) перерисовывает её горизонтальными сканлайнами 12 раз
в секунду.

Правила, нарушение которых ломает картинку:

- **Корпус маскота неподвижен.** Сдвиг тела на долю строки (6 px) заново
  раскладывает всю фигуру по сканлайнам, и она «скачет». Двигаются только
  бобины, хвост, лапки (не больше 8 единиц сцены) и моргание.
- Форма передаётся **тоном**: светлое — тонкие линии, чёрное — сплошные блоки.
  Чисто белые участки шейдер не рисует вовсе.
- Шум рваных краёв меняется раз в 8 шагов, а не каждый кадр.
- Вне экрана и во скрытой вкладке анимация на паузе; при reduced motion —
  один статичный кадр; без WebGL — обычный canvas.

## 9. Тестирование

Тесты лежат рядом с кодом (`*.test.ts(x)`), запускаются `npm test`
и не требуют backend.

| Что                                             | Как                                                                                  |
| ----------------------------------------------- | ------------------------------------------------------------------------------------ |
| Чистые функции (`shared/lib`, `features/*/lib`) | обычные unit-тесты, граничные значения                                               |
| Слайсы                                          | редьюсер + селектор на корневом состоянии `{ [reducerPath]: state }`                 |
| API-адаптеры                                    | `mockBaseQuery` и `createHybridBaseQuery` с поддельным `http` и `vi.useFakeTimers()` |
| Компоненты                                      | Testing Library: роли и доступные имена, не CSS-классы                               |

Компонентам нужен локальный store: `configureStore({ reducer: combineSlices(baseApi, …) })`.
Импортировать store из `app` нельзя (правило FSD).

## 10. Рабочий цикл агента

Для каждой задачи:

1. **Изучить.** Прочитать задачу, затронутые слайсы и их `index.ts`. Если
   задача касается API — сверить контракт с кодом backend.
2. **Спланировать.** Определить слой для каждого изменения по таблице из
   раздела 4. Не создавать абстракций «на будущее».
3. **Реализовать** маленькими шагами, соблюдая разделы 4–8.
4. **Проверить автоматически** (из `frontend/`):

   ```sh
   npm run typecheck && npm run lint && npm run lint:fsd && npm run format:check && npm test && npm run build
   ```

5. **Проверить глазами.** Запустить `npm run dev` (или стек Docker из
   `infra/README.md`) и пройти сценарий в браузере: ширина 1440 и 390 px,
   консоль без ошибок, клавиатурная навигация, видимый фокус.
6. **Отчитаться:** что сделано, как проверено, что не удалось проверить и
   почему. Не писать «готово», если какая-то проверка не запускалась.

### Definition of Done

- все команды из шага 4 зелёные;
- сценарий пройден в браузере на двух ширинах, ошибок в консоли нет;
- новые состояния (загрузка, ошибка, пусто) нарисованы;
- интерактивные элементы доступны с клавиатуры и имеют доступные имена;
- имитация, если появилась, помечена в интерфейсе;
- `README.md` описывает фактическое поведение.

## 11. Git

- Ветка от актуального `dev`: `feature/frontend-<задача>`.
- Conventional Commits со scope `frontend`:
  `feat(frontend): add highlight timeline`, `fix(frontend): stop mascot jitter`,
  `test(frontend): cover hybrid api routing`, `docs(frontend): describe api modes`.
- Коммиты маленькие и законченные; PR — в `dev`, в описании — что сделано,
  как проверено, скриншоты.
- Прямой push в `main` и `dev` запрещён.

## 12. Запрещено

- Коммитить `node_modules`, `dist`, `.env*` (кроме `.env.example`),
  скриншоты, тестовые видео.
- Хранить в коде ключи и секреты: у клиента их быть не может в принципе,
  всё приватное живёт в backend.
- Показывать сгенерированные данные как настоящие.
- Обходить ESLint/Steiger через `eslint-disable` без комментария с причиной.
- Ломать режим `mock`: интерфейс должен работать без backend.
