# Backend ClipHunter

Текущий этап предоставляет устанавливаемое приложение FastAPI, настройки
окружения, метод проверки работоспособности, API проектов и документацию API. Проекты
сохраняются в PostgreSQL через SQLAlchemy 2.0; схема управляется Alembic.
Потоковая загрузка сохраняет оригиналы в S3-совместимое хранилище MinIO/R2.
Обработка видео, ИИ и нарезка появятся позже.

## Архитектура

Пакет `src/cliphunter` разделён на четыре слоя:

| Пакет | Назначение |
| --- | --- |
| `domain` | Бизнес-сущности и интерфейсы репозиториев; только стандартная библиотека |
| `application` | Сценарии использования, DTO и интерфейсы сервисов; зависимости направлены внутрь |
| `infrastructure` | Настройки, SQLAlchemy, S3, временные файлы и ffprobe |
| `presentation/http` | HTTP-маршруты и схемы ответов Pydantic |

`main.py` связывает компоненты через фабрику `create_app()`. Domain содержит VideoProject, TranscriptSegment, Highlight и GeneratedClip.
Application реализует создание, получение, список проектов и загрузку видео
через интерфейсы репозитория, транзакции и внешних сервисов; доступ к SQLAlchemy остаётся в infrastructure. Метод проверки состояния
не содержит бизнес-логики и не требует отдельного сценария или репозитория.

Для запуска используются Python 3.12–3.14, FastAPI, Pydantic v2/settings, Uvicorn, SQLAlchemy 2.0, asyncpg, Alembic, boto3 и ffprobe.
Для тестирования и проверок — Pytest, HTTPX2 (Starlette TestClient), Ruff и MyPy.
При запуске без Docker установите FFmpeg, включая исполняемый файл `ffprobe`.
В контейнере эти инструменты уже установлены; сейчас используется только проверка метаданных.
Версии прямых и транзитивных зависимостей приложения закреплены в
`requirements.lock`; инструменты разработки в Docker-образ не устанавливаются.

## Запуск без Docker

Выполните из корня репозитория, используя Python 3.12+:

```sh
python3 -m venv backend/.venv
. backend/.venv/bin/activate
python -m pip install -c backend/requirements.lock -e './backend[dev]'
cp .env.example .env
python -m cliphunter
```

Если `.env` уже настроен, сохраните его вместо повторного копирования примера.
Приложение читает `.env` из текущего рабочего каталога; переменные окружения
процесса имеют приоритет. Для чтения общего `.env` запускайте API из корня
репозитория. Сейчас используются следующие настройки:

| Переменная | По умолчанию | Проверка |
| --- | --- | --- |
| `APP_ENV` | `development` | `development`, `test` или `production` |
| `APP_HOST` | `0.0.0.0` | Непустой адрес для запуска сервера |
| `APP_PORT` | `8000` | Целое число от 1 до 65535 |
| `DATABASE_URL` | Не задано | URL PostgreSQL с драйвером `postgresql+asyncpg` |

Для API проектов требуется `DATABASE_URL`. Без него health и Swagger доступны,
а API проектов возвращает 503. Для запуска на компьютере замените в URL имя
`postgres` на `localhost`. Для загрузки задайте `S3_ENDPOINT_URL`, `S3_ACCESS_KEY`, `S3_SECRET_KEY`,
`S3_BUCKET` и `S3_REGION`. При запуске на компьютере endpoint локального MinIO —
`http://localhost:9000`; внутри Compose — `http://minio:9000`. Ключи должны иметь
доступ к закрытому бакету. API не создаёт бакеты автоматически. Остальные
зарезервированные значения относятся к будущей интеграции с ИИ. Полные настройки и переменные окружения нельзя записывать в логи.
Развёртывание в production будет подготовлено отдельно.

Для автоматического перезапуска при изменениях выполните из корня репозитория
в активированном окружении:

```sh
python -m uvicorn cliphunter.main:create_app --factory --reload --host 127.0.0.1 --port 8000
```

## Контракт API

`GET /api/v1/health` возвращает HTTP 200 с типом `application/json`:

```json
{"status": "ok"}
```

Метод проверяет работу процесса API. Готовность базы и хранилища проверяется
отдельно. Авторизация и обработка видео ещё не реализованы.

- Swagger UI: http://localhost:8000/docs.
- OpenAPI: http://localhost:8000/openapi.json.

Доступные методы:

| Метод | Адрес | Результат |
| --- | --- | --- |
| POST | `/api/v1/projects` | Создать проект из JSON `{"title":"Мой стрим"}`, ответ 201 |
| GET | `/api/v1/projects?limit=20&offset=0` | Список: `items`, `total`, `limit`, `offset` |
| GET | `/api/v1/projects/{id}` | Данные проекта |
| GET | `/api/v1/projects/{id}/status` | Статус и время его обновления |
| POST | `/api/v1/projects/{id}/upload?filename=stream.mp4` | Загрузить видео и вернуть проект |

Новый проект имеет статус `created`, поля видео равны `null`. После успешной
загрузки — `uploaded`, исходное имя, размер в байтах и длительность в секундах.
Состояние сохраняется в PostgreSQL. При ошибке загрузки проект остаётся `created`
и допускает повторную попытку. Внутренний
ключ хранилища не входит в ответ. Для списка допустимы `1 <= limit <= 100`
и `offset >= 0`; порядок — от новых проектов к старым.

Ошибки имеют вид `{"error":{"code":"not_found","message":"Проект не найден"}}`.
Используются 404 для отсутствующих проектов, 422 для неверных параметров
и 503 при недоступной базе или хранилище. В ответах нет SQL, паролей и исходных данных ошибок.

## Потоковая загрузка

В `POST /api/v1/projects/{id}/upload` передавайте **двоичное тело видео**, имя
в query-параметре `filename` и соответствующий `Content-Type`. Имена с кириллицей
нужно кодировать как обычные параметры URL. Запросы multipart не поддерживаются:
это позволяет ограничивать поток до разбора и записи всего тела на диск.
Поддерживаются `Content-Length` и HTTP chunked transfer; лимит проверяется
по фактически принятым байтам и при отсутствии заголовка длины.

| Расширение | Content-Type |
| --- | --- |
| `.mp4` | `video/mp4` |
| `.m4v` | `video/mp4` или `video/x-m4v` |
| `.mov` | `video/quicktime` |
| `.mkv` | `video/x-matroska` |
| `.webm` | `video/webm` |

Расширение и MIME дополняются проверкой реального контейнера, видеопотока
и длительности через `ffprobe`. Повреждённые, пустые и аудиофайлы отклоняются.
Временный файл записывается порциями, проверяется свободное место и затем
выполняется S3-загрузка частями по 8 МиБ. Весь файл в память не загружается.
Текущие объекты закрыты и не выдаются для скачивания через API.

| Настройка | По умолчанию | Назначение |
| --- | --- | --- |
| `MAX_UPLOAD_SIZE_MB` | 500 | Размер в МиБ, от 1 до 10240 |
| `MAX_VIDEO_DURATION_SECONDS` | 1800 | Максимальная длительность |
| `UPLOAD_DISK_RESERVE_MB` | 64 | Свободный резерв временного диска в МиБ |
| `UPLOAD_TEMP_DIR` | Системный временный каталог + `cliphunter-uploads` | Каталог приёма видео |
| `MAX_CONCURRENT_UPLOADS` | 2 | Одновременные временные файлы на процесс API |
| `UPLOAD_TIMEOUT_SECONDS` | 900 | Предельное время запроса загрузки |
| `FFPROBE_TIMEOUT_SECONDS` | 20 | Предельное время проверки метаданных |
| `S3_TRANSFER_TIMEOUT_SECONDS` | 300 | Срок передачи в S3, проверяемый по прогрессу |

Ошибка размера возвращает 413, MIME/расширения — 415, содержимого или
длительности — 422, нехватки диска — 507, срока запроса — 408. Недоступность S3
возвращает 503, повторная или конкурентная загрузка — 409. После успешной загрузки
статус меняется на `uploaded`; фоновой обработки на этом этапе ещё нет.

Транзакция блокирует изменение проекта на время загрузки. При ошибках временный
файл удаляется, транзакция откатывается, а частично сохранённый объект удаляется
по возможности. При неоднозначном ответе на COMMIT сначала проверяется запись
в новой транзакции. Если база в этот момент недоступна, объект сохраняется,
чтобы не удалить уже подтверждённое видео; событие фиксируется для сверки после
восстановления сервиса. Отдельной фоновой сверки пока нет. У S3-запросов ограничены
число попыток и сетевые таймауты; остановка синхронной SDK-передачи может завершиться
после текущего сетевого запроса. Временный файл остаётся до окончания передачи.

## Проверки

Активируйте окружение разработки и выполните из каталога `backend/`:

```sh
ruff check .
ruff format --check .
mypy src
pytest
```

Модульные тесты проверяют сущности, сценарии, HTTP-контракт и настройки без
внешних сервисов. Интеграционные тесты репозитория и ограничений требуют отдельной
базы PostgreSQL с применёнными миграциями. Задайте её URL в `TEST_DATABASE_URL`;
без него эти тесты пропускаются. Настоящие внешние API-ключи не нужны. GitHub Actions
запускает проверки на Python 3.12 и 3.13, а также отдельно собирает и проверяет
полный стек Docker Compose. Проверяются настоящий MP4, chunked HTTP,
`ffprobe`, PostgreSQL, multipart-загрузка MinIO и совпадение SHA-256 объекта.
Тест удаляет только собственные проекты и объекты. Повторить его из корня:

```sh
docker compose --env-file .env -f infra/docker-compose.yml exec -T api python - < backend/tests/integration/smoke_upload.py
```

## Миграции базы данных

Из корня репозитория с активированным окружением и настроенным `DATABASE_URL`:

```sh
alembic -c backend/alembic.ini upgrade head
alembic -c backend/alembic.ini check
```

Compose выполняет миграции отдельным одноразовым сервисом `migrate` до запуска
API. Автоматического `create_all` в приложении нет. Начальная миграция создаёт
проекты, сегменты транскрипции, хайлайты и клипы с ограничениями, индексами
и каскадным удалением. Создавайте новые миграции через `revision --autogenerate`,
проверяйте полученный код и не изменяйте уже применённые ревизии.

Запуск в контейнерах описан в [документации инфраструктуры](../infra/README.md).
